## the outcome world

### before

```ts
import { asHashSha256 } from 'hash-fns';

const hash = await asHashSha256('hello world');
// works on node ✅
// works on bun ✅ (bun polyfills node crypto)
// works in browser ❌ — crypto.createHash is not a function
// works in deno ❌ — needs --allow-read for node compat
// works in cloudflare workers ❌ — no node crypto
// works in react native ❌ — no node crypto
```

hash-fns today is node-locked. it uses `import crypto from 'crypto'` under the hood. anyone who reaches for it in a browser, edge function, or react native app hits a wall.

### after

```ts
import { asHashSha256 } from 'hash-fns';

const hash = asHashSha256('hello world');
// works on node ✅
// works on bun ✅
// works in browser ✅
// works in deno ✅
// works in cloudflare workers ✅
// works in react native ✅
// sync ✅ — no await needed
```

hash-fns becomes universal. one import, one api, every runtime. the pit of success widens from "node developers" to "javascript developers."

### the "aha" moment

you build a feature that needs content-addressable hashes. the backend uses `hash-fns` for deduplication. now you need the same hash in the browser for optimistic cache keys. today, you'd reach for a second library or polyfill. after this change — same import, same result, zero config.

## user experience

### usecases

| goal | contract | example |
|------|----------|---------|
| fingerprint content for dedup | `asHashSha256(message)` | `asHashSha256('invoice-pdf-bytes')` → deterministic hex string |
| compact cache key | `asHashShake256(message, { bytes: 16 })` | 32-char hex key for cdn cache |
| ~~quick non-secure fingerprint~~ | ~~`asHashMd5(message)`~~ | dropped in v3 — md5 is cryptographically broken; use sha256 instead |
| validate a hash string | `isHashSha256(input)` | assert format before database insert |

### contract changes

**inputs**: unchanged — still `(message: string)` and `(message: string, options?)`.

**outputs**: unchanged — still returns `Hash` (branded string, hex encoded).

**break: sync by default**:

before:
```ts
const hash = await asHashSha256('hello'); // async
```

after:
```ts
const hash = asHashSha256('hello'); // sync — no await
```

noble/hashes is synchronous. hash functions complete in microseconds — async overhead is waste. `asHashSha256Sync` becomes redundant; `asHashSha256` itself becomes sync.

this is a semver major bump. callers that `await` a sync return get the value (no runtime error), but callers who `.then()` on it will break. worth it — the api becomes simpler and more honest.

### timeline

1. swap `crypto.createHash` → `@noble/hashes` (sha256, shake256)
2. drop md5 entirely (cryptographically broken, noble won't ship it, no legitimate use in new code)
3. make async functions sync (noble is sync by design)
4. remove the `Sync` suffix variant (now redundant)
5. bump to v3.0.0 (skip v2)

## mental model

### how users describe it

> "hash-fns gives me typed hashes that work everywhere — node, browser, edge, wherever. i just call `asHashSha256('data')` and get a hex string back. no polyfills, no runtime checks, no async noise."

### analogy

hash-fns is like a pocket calculator for hashes. you don't need to know if you're in an office or on the beach — it just works. the swap from node crypto to noble/hashes is like the swap from a desk calculator that needs a wall outlet to a solar-powered one. same buttons, same answers, runs anywhere there's light.

### terms

| user says | we say | what it does |
|-----------|--------|---------|
| "hash it" | `asHashSha256(msg)` | produce a sha256 hex digest |
| "is this a hash?" | `isHashSha256(str)` | type guard + format check |
| "short hash" | `asHashShake256(msg, { bytes: 16 })` | variable-length via shake256 |
| "works in the browser" | isomorphic | same code, any js runtime |

## evaluation

### how well does it solve the goals?

| goal | score | note |
|------|-------|------|
| isomorphic (browser + node) | ✅ | noble/hashes is pure js, zero deps, runs everywhere |
| pit of success | ✅ | sync api removes async footgun; branded types remain |
| perf parity | ✅ | sha256: ~1.13M vs ~1.16M ops/sec — negligible diff |
| supply chain | ✅ | noble is audited (cure53), zero transitive deps |
| bundle size | ✅ | sha256 alone: ~7KB min — trivial for browsers |

### pros

- **universal**: one package for every js runtime
- **simpler api**: sync removes unnecessary async ceremony
- **audited**: cure53 audited noble/hashes; same trust level as openssl
- **zero native deps**: no node-gyp, no compilation, no c++ bindings
- **smaller surface**: pure js is easier to audit than openssl binds

### cons

- **sha512 is ~2x slower**: noble pure-js vs node's c++ openssl. irrelevant for hash-fns today (we don't expose sha512), but worth a note if we ever do.
- **major version bump**: sync api change breaks `.then()` callers. acceptable — async hash computation was always a lie (microsecond operations don't need async).
- **md5 dropped**: md5 is cryptographically broken and noble won't ship it. removed entirely in v3 — no deprecation period, clean cut.

### edgecases & pit of success

| edgecase | how we handle it |
|----------|-----------------|
| caller awaits a sync function | js resolves non-promise values in await — no runtime error, just unnecessary microtask |
| caller `.then()`s a sync function | runtime error — this is the break; semver major covers it |
| unicode input | noble/hashes accepts `Uint8Array`; we encode string → utf8 bytes via `TextEncoder` (universal, no node buffer needed) |
| empty string | valid input — produces the known empty-string hash (covered by tests) |
| md5 callers | removed in v3 — callers must migrate to sha256 or shake256 |
| large input (>1GB) | sync block concern — but same as node crypto sync. not a regression |
